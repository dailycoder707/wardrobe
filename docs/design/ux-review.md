# UX Review — Self-Critique

Written as a hostile reviewer of this same design, per the Constitution's standing
review prompt (`phase-1-architecture.md` Section 4). Not defended — every risk below
is real, not a strawman set up to be easily solved.

## Top 10 UX risks

**1. The portrait-tablet-first bet (Section 0) might just be wrong.** This entire
document assumes the wardrobe-door mount is portrait. If it's actually mounted
landscape, every "primary" wireframe in `screen-specifications.md` is the secondary
orientation in practice, and the split-screen layouts (Outfit Builder, Garment
Detail) that were designed to make good use of landscape's extra width become the
*common* case rather than the occasional one.
**Mitigation**: both orientations are fully specified, not just portrait with a
landscape afterthought — but the actual mount should be confirmed (a literal
tape-measure-and-photo check of the wardrobe door) before Phase 5 locks anything in,
since it's cheap to verify and expensive to have designed backwards.

**2. The dashed-border visual language is overloaded.** It means "an AI-guessed
attribute, tap to confirm/edit" on a Confidence Chip, and it means "this weather data
is stale" on the Weather Chip — two meanings, one visual signal. A user who learns
"dashed = tap to fix" from garment attributes may tap a stale weather chip expecting
the same editable interaction and get nothing.
**Mitigation**: keep the dashed border only for the "provisional data" meaning both
cases genuinely share, but make the *interaction* explicit in the weather chip's
copy itself ("· yesterday's forecast" is inert text, not a tappable affordance) —
already partially designed this way in `component-library.md`; Phase 5 should
resist the temptation to make the weather chip tappable "for consistency," since
consistency of appearance without consistency of behavior is worse than two distinct
appearances.

**3. Wishlist's discoverability is genuinely low.** It lives as a segmented tab
inside Closet (a deliberate IA choice to avoid a 6th dock icon), but a first-time
user has no reason to look for a "Wishlist" tab at the top of a screen they opened to
browse their existing closet — it could go unused simply because it's never noticed.
**Mitigation**: this is a real tradeoff, not a free win — accepted deliberately in
`navigation-flow.md`, but Phase 5 should add one small nudge (e.g. Home's "Add to
Wishlist" appearing as a quick action occasionally) rather than relying on the tab
alone to be found.

**4. Dual input paths for grid density (pinch and the stepper) can drift out of
sync in a user's mental model.** If pinching mid-gesture doesn't visually confirm
which discrete column-count it will snap to until release, a user might expect a
different result than they get, and not understand why the stepper's icons don't
obviously match whatever density pinching landed on.
**Mitigation**: the stepper's active icon must always reflect the *current* density
live, including immediately after a pinch gesture ends — this needs explicit
attention in Phase 5, not just "wire both up to the same state and assume it's fine."

**5. Gap Analysis may still land as criticism despite the copy work.** "A few things
your closet doesn't quite cover yet" is gentler than "gaps," but showing someone a
list of what they *don't* own, generated by their own app, unprompted, risks feeling
judgmental no matter how the sentence is worded — tone alone may not fully solve a
structural framing problem.
**Mitigation**: Gap Analysis is a tab the user navigates to deliberately (Wardrobe
Story → Gap Analysis), never surfaced unprompted on Home or as a notification — this
containment matters as much as the copy. Keep it that way; resist ever promoting a
gap insight onto Home "for engagement."

**6. No onboarding means genuinely new gestures (pinch-to-resize, drag-and-drop
layering) have zero discovery mechanism.** The philosophy explicitly rejects
onboarding-carousel patterns (Section 1) — but that also means there's no moment that
ever tells this app's one user "you can pinch this grid" or "you can drag garments
onto these slots." Even a single dedicated user has to stumble onto both by accident,
or never learn them at all.
**Mitigation**: reject a full onboarding flow, but keep one narrow exception — a
single, dismissible, one-time inline hint the very first time each screen (Closet,
Outfit Builder) is opened ("Pinch to change how much you see at once" / "Drag pieces
here to build a look"), gone after first dismissal, never shown again, never a
tutorial overlay blocking the screen. This is a real addition to the spec, not
currently covered anywhere above — flagged here so Phase 5 doesn't skip it.

**7. Home's outfit-suggestion reasoning is the only place weather context surfaces
at all.** The styling engine uses weather to filter/score suggestions everywhere
(Outfit Builder's suggestion strip, "Style this item"), but the *visible* weather
chip only lives on Home. A suggestion appearing in Outfit Builder with no visible
weather context nearby may feel arbitrary compared to Home's explained version.
**Mitigation**: the suggestion strip in Outfit Builder (screen spec §8) should carry
the same short one-line rationale Home's hero card gets, not just a bare row of
tiles — this is implied by "explainable, no black-box suggestions"
(`phase-1-architecture.md` Section 6) but should be made explicit here: every
surfaced suggestion, everywhere, gets its one-line why.

**8. Long-press-to-multi-select has poor discoverability**, same category of problem
as risk 6 but specific to Closet's bulk-status-change flow — long-press affordances
are notoriously easy to never stumble onto.
**Mitigation**: add an explicit "Select" action in Closet's overflow menu that enters
the same multi-select mode, so long-press is a shortcut for people who know it
exists, not the only path.

**9. "Today's Inspiration" risks feeling stale or repetitive faster than intended.**
A small starter set of rotating lines (`microcopy-guide.md` lists three) will start
repeating within days for daily use on a permanently-mounted device — the opposite of
the "handcrafted, personal" feeling it's meant to create.
**Mitigation**: either commit to writing a genuinely large set (50+) before this
ships, or cut the feature from v1 rather than ship a visibly-repeating version of it
— a small repeating set actively undermines the "premium, considered" tone more than
not having the feature at all. Flagged as a real decision point for whoever
implements Phase 5, not resolved here.

**10. The RESTRICT-blocked delete could be discovered as a dead disabled button if
Phase 5 doesn't implement it exactly as specified.** The design calls for an inline
explanation next to a disabled Delete action (screen spec §5), but it would be easy
to implement as a plain greyed-out menu item with no explanation, or a delete attempt
that only fails after the fact with a raw error.
**Mitigation**: this needs explicit test coverage in Phase 8 — "attempt to delete a
garment with wear history, assert the explanation text is shown" — not just a visual
design note that's easy to lose between phases.

## What would confuse a first-time user

- Not realizing Wishlist exists inside Closet (risk 1... risk 3 above).
- Not knowing pinch-to-resize or drag-and-drop are possible (risk 6).
- Seeing a dashed-border chip and not knowing whether it's tappable in every
  context (risk 2).
- The difference between "Saved Looks" (Outfits tab) and "Wardrobe Story" (a
  fundamentally different kind of content — outfits vs. reflective stats) if the
  naming isn't kept clearly distinct in the actual UI copy.
- Why a delete action is greyed out, if risk 10's mitigation isn't followed.

## What can be simplified

- **Today's Inspiration** could be cut entirely for v1 (risk 9) — it's the single
  lowest-value, highest-maintenance-cost element in the Home screen spec relative to
  everything else on it.
- **The Wear History / Calendar list-toggle** could arguably be one screen with a
  view switch rather than two named screens in the requirements list — already
  designed this way (`navigation-flow.md`), worth confirming Phase 5 doesn't
  accidentally build two independently-diverging screens instead of one screen with
  a toggle.
- **Grid "smart grouping" mode** (Closet, §4) is an optional, non-default toggle that
  adds real implementation complexity (section headers interleaved with a
  Paging-3-backed grid) for a feature that isn't the default experience — worth
  reconsidering whether it earns its cost versus simply shipping the ungrouped grid
  and adding grouping later if it turns out to be missed.
